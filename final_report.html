Summary. We built a key-value table that writes through an LSM tree and stores every sorted run as an ordinary Iceberg data file in Avro, with a bloom filter and an exact key index in Iceberg's Puffin format. Runs are merged level by level (compaction) with Iceberg rewrite commits. With 100,000 keys and 400,000 streaming updates, a point lookup takes 0.139 ms and reads about one block, against 75.8 ms for Iceberg append (545× slower), 797 ms for merge-on-read and 30.7 ms for copy-on-write. Writes run at 131,089 per second. The table stays a normal Iceberg table: Spark reads it, runs SQL analytics on it and time-travels through its snapshots without any of our code.

1. Problem

Iceberg picks the files a query reads from the min and max of each column in each file. When updates stream in with random keys, every new file covers almost the whole key range, so a lookup of one key opens every file. Iceberg's two update modes trade this off badly: merge-on-read keeps writes cheap but readers must apply a growing pile of delete files; copy-on-write keeps reads cheap but every batch rewrites most of the table. An LSM tree is the standard answer for update-heavy key-value workloads. Our goal was to build one inside Iceberg's format, so the data stays readable by every Iceberg engine.

2. Design

put/delete ─► WAL (CRC32 records) ─► MemTable (skip list) ──flush──► L0 run: sorted Avro file + Puffin index │ (one Iceberg append commit) get(key) ─► MemTable ─► L0 runs, newest first ─► one run per level ▼ key range ─► bloom filter ─► key index ─► one block L1 … Ln: sorted, non-overlapping runs ▲ (leveled merges = Iceberg rewrite commits)
  • Write path. Each write gets a sequence number, goes to the write-ahead log, then to the in-memory skip list. A full memtable is written as one key-sorted Avro file (a run). One Iceberg transaction appends the file and moves the table property lsm.manifest-location to a new version of our level manifest (JSON), so the data and the LSM state change atomically.
  • Avro runs. We write the Avro blocks ourselves (about 64 KB each, uncompressed) and record the byte offset where each block starts, so a lookup seeks straight to one block and decodes it in one pass. We also store key, seq and op bounds in the Iceberg metadata, which Iceberg's own Avro writer does not do, so other engines can prune our files.
  • Puffin index. Each run's Puffin file holds three blobs: a bloom filter (1% false positives), an exact key index (open-addressing hash table: key fingerprint → block, row; 12 bytes per slot, 17–34 bytes per key; 3.1 MB for all runs of this table) and a block directory (first key, offset and row count of each block, for range scans). The Puffin file is attached to the run's snapshot with updateStatistics(). If it is lost, the index is rebuilt from the data file.
  • Read path. Memtable, then L0 runs newest first, then at most one run per deeper level (their key ranges don't overlap). In a run: range check, bloom filter, key index → read the one block and the row it names. A key the run doesn't hold costs no I/O. The first version found wins, and a delete marker (tombstone) hides older versions.
  • Merges (compaction). Leveled, as in RocksDB. When L0 has 4 runs, they are k-way merged with the overlapping L1 runs; a level over its size limit (10× the level above) pushes one run down, round-robin over the key space. Only the newest version of each key survives, and tombstones are dropped when no deeper level can hold the key. Each merge is one Iceberg newRewrite() commit (operation replace) that also moves the manifest pointer. Old files remain reachable from older snapshots.
  • Range scans k-way merge the memtable and the overlapping runs. Crash recovery replays log records newer than the last flushed sequence number.

Iceberg (1.10) is used unmodified, only through its public Java API: catalog, transactions, append, rewrite, table properties, snapshot summaries, Puffin and statistics files. About 3,400 lines of Java plus 400 lines of tests (19 automated tests).

Reading the results. Lookups in plain Iceberg get slower as files pile up, because every file's key range covers every key. Merge-on-read is the slowest reader, because every lookup also opens the delete files. Copy-on-write reads one file, but it must scan that whole file, and every batch rewrites most of the table: its batches write 2.91 rows per user write against our 1.57, and that cost grows with the table, since a batch of random keys touches every file. At our table size the rewrite is still cheap, which is why copy-on-write's write speed looks good here. Our table reads one block of one file and stays flat as the table grows. Without merges our point lookups stay fast at this size, because the bloom filter and key index rule out runs in memory. Merges matter for everything else: they cut our files from 17 to 5, make range scans 8× faster, remove old versions and deleted keys, and let other engines prune files (Section 5), at the price of writing each row about twice. Append is the fastest writer because it does no sorting, no log and no indexing.

Merge totals for our table in this run: 4 merges, 290,118 old versions and 19,193 tombstones removed, 0.77 s spent merging. Final shape: L0: 1 runs (11,170 entries) | L1: 4 runs (90,689 entries).

5. Use case: a customer-profile store with Spark analytics

An online shop streams change events (CDC) for 50,000 customers: sign-ups, plan changes, city moves, purchases and account closures, 200,000 events in all. The current profile of each customer lives in one LSM-Iceberg table (./run.sh usecase). Two kinds of users read the same table, with no copy in between:

  • The support app looks customers up by id through our read path: p50 0.160 ms before the merge and 0.147 ms after it. Ingest ran at 72,708 writes per second.
  • Analysts use Spark SQL (./run.sh spark, Spark 3.5 with the Iceberg runtime 1.10). Spark sees the LSM history in the snapshots metadata table (flushes as append, merges as replace), builds a "current customers" view (newest seq per key, deletes dropped) and computes revenue by city and plan in 0.240 s. Time travel (VERSION AS OF) shows the 224,884 rows stored before the merge against 48,999 after it, for 48,999 live customers.
  • Merges help Spark too. Before the merge Iceberg plans 19 files for a lookup of one customer; after it, 1. Merged runs have disjoint key ranges and our Avro files carry key bounds, so Iceberg's ordinary min/max pruning works for any engine. The Spark lookup took 0.069 s before and 0.030 s after (mostly Spark's fixed job overhead).

6. Related work

Apache Paimon and Apache Hudi (merge-on-read tables) also bring LSM-style ingestion to lakehouse storage, but each with its own table format. Iceberg's built-in answers are the merge-on-read and copy-on-write modes we compare against. Iceberg's Puffin spec reserves room for indexes, and a proposal on the Iceberg dev list adds Puffin bloom filters for file skipping during scan planning; released Iceberg (1.10) does not use them yet. Our work shows such an index, plus a key → row index and leveled merges, working on the unmodified format.

7. Limitations and future work

  • One writer at a time; merges run inline after a flush, so a write that triggers a merge waits for it. A background merge thread is the next step.
  • Spark reads the table but does not use our Puffin key index; doing that needs a change to Iceberg's scan planning (the dev-list proposal above) or a custom Spark data source.
  • Snapshot expiry would delete the Puffin files of expired snapshots; our tables rebuild a missing index on open (tested), which is correct but slow. A production version would re-attach live indexes to the newest snapshot.
  • Avro runs are uncompressed for lookup speed, so they take more space than zstd Parquet. A light codec is one setting away.
  • Measured on a laptop with a local disk, not on object storage.

8. Use of AI

Our work. The idea and the design are ours. As a team we discussed the problem and decided how to build the LSM tree on Iceberg: storing runs as Iceberg data files, keeping the index in Puffin, committing flushes and merges as Iceberg snapshots, the leveled merge policy, the baselines to compare against and the Spark use case. We split this into features and worked through them one at a time.

AI's work. We used an AI coding assistant to write the code. For each feature we gave it a prompt such as "implement this feature" with our design for it, then ran the code, checked the output and asked for changes until it worked as we intended. The assistant also helped draft the text of this report from our results.
