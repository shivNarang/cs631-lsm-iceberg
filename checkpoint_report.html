1. Goal (recap)

Iceberg skips files using per-file min/max column statistics. Under streaming upserts each micro-batch file covers almost the whole key space, so min/max pruning skips nothing and a point lookup reads every file. We add LSM-tree structure (write buffer, sorted runs, bloom filters, fence pointers, and later compaction) on top of Iceberg while keeping the table readable by any Iceberg engine. Implementation: Java 17 on the reference Apache Iceberg Java library (1.10), the same library Spark, Flink and Trino use.

3. How it works

Iceberg table schema: key string, value string, seq long, op int (op 0 = put, 1 = delete), declared sort order key ASC. It is a normal Iceberg table, so Spark or Trino can read it. The current value of a key is the row with the highest seq.
  • Write: each put/delete gets a global sequence number, is appended to the WAL, then inserted into the skip-list MemTable (newest version per key; deletes become tombstones).
  • Flush: the MemTable is written as a key-sorted Parquet file (zstd) through Iceberg's Parquet writer. One Iceberg Transaction then (a) newAppend() adds the run, with the snapshot summary tagged lsm.operation=flush, lsm.run-id, lsm.level, lsm.min/max-key, and (b) updateProperties() moves lsm.manifest-location to a new LSM level manifest. Either both happen or neither does. The run's Puffin file (bloom filter blob at 1% FPR + fence-pointer blob) is then registered on that snapshot with updateStatistics(), and the WAL is truncated.
  • Point lookup: MemTable → L0 runs newest first. Per run: key-range check → bloom filter → binary search over fence pointers → read exactly one Parquet row group. The first version found wins, and a tombstone means the key was deleted.
  • Range scan: k-way heap merge of the MemTable and the overlapping row groups of each run, ordered by (key, −seq).
  • Recovery: on open, WAL records with seq > the committed lastSeq are replayed, so a crash between the commit and the WAL truncation loses nothing. A torn last WAL record fails its CRC and is ignored, and a missing Puffin index is rebuilt from Parquet.

Both tables gave identical answers on every lookup. Main finding: vanilla lookup cost grows with the number of files (39 → 133 ms), while ours stays flat (~0.34 ms) because about one block is read per lookup. Caveats: vanilla latency includes Iceberg query planning (reading manifests) on every query. Our writes are ~2× slower because of the per-record WAL append and the sort. Before compaction, the LSM read cost still grows slowly with the number of runs.

5. Remaining work (plan to final demo)

  • Compaction (next): leveled compaction with size ratio 10. Merge overlapping L0 runs into non-overlapping L1 runs, drop shadowed versions, and purge tombstones at the last level. Commit with Iceberg's newRewrite() (delete old files and add new ones atomically) together with the new LSM manifest. Run it as a background thread.
  • Spark integration: a resolved "latest value" view, and routing point lookups through our Puffin index.
  • Full evaluation: YCSB workloads A/B/C/E and a modified TPC-H; write latency, read latency, write amplification and file count over time. Compare against vanilla Iceberg copy-on-write and merge-on-read (equality deletes).
  • Concurrent commits (retry on conflict); background flush on a separate thread.
