The problem

Iceberg decides which files to read using the min and max value of each column in each file. That works when data arrives roughly sorted. With streaming updates, every small file contains keys from all over the key space, so every file's min/max range covers almost everything. A lookup for a single key then has to open every file. We are adding LSM-tree ideas to Iceberg so that a lookup only touches the file that actually has the key, while the table stays a normal Iceberg table that Spark or Trino can still read.

How it works

  1. Writes go to a log file on disk (so nothing is lost in a crash), then into a sorted in-memory buffer.
  2. Flush: when the buffer is full, it is written out as one Parquet file sorted by key, and added to the Iceberg table in a single commit. For each file we also store a small index, made of a bloom filter (which can say that a key is definitely not in the file) and the first key of each block in the file. The index goes in Iceberg's own index file format (Puffin) and is attached to that commit.
  3. Lookups check the buffer first, then the files from newest to oldest. A file is skipped if the key is outside its range or its bloom filter says no. Otherwise we read only the one block that can hold the key. The newest version wins, and deleted keys are marked so older versions stay hidden.
  4. Range scans merge the buffer and the relevant blocks of each file in key order.
  5. Crash recovery: on restart, any writes in the log that were not yet flushed are replayed.

Both tables returned the same answer for every lookup. The main result is that plain Iceberg gets slower as files pile up (39 ms with 12 files, 133 ms with 20), while our lookups stay around 0.3 ms. The trade-off is that writes are about 2× slower, because every write goes to the log and every flush sorts its data.

Next steps

  • Compaction: merge older files into larger sorted, non-overlapping ones, dropping old versions and deleted keys. Without this, the number of files keeps growing.
  • Spark integration, so queries run through Spark can use our index.
  • Full evaluation with standard workloads (YCSB, modified TPC-H), measuring read/write latency and how much extra data we write, compared against Iceberg's built-in update modes.
